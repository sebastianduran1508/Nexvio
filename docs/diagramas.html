RLS - Propagacion de tenant (secuencia)

%% ===================================================================== %% NEXVIO - Propagacion del contexto de tenant (RLS) - Diagrama de secuencia %% Muestra como una peticion viaja desde el cliente hasta PostgreSQL %% aplicando el filtro organizacion_id via RLS, sin que el codigo de %% negocio tenga que anadir WHERE organizacion_id = ... manualmente. %% Requiere Mermaid >= 8. %% ===================================================================== sequenceDiagram autonumber actor U as Usuario (rol X) participant C as Cliente (Expo / Next.js) participant G as AuthGuard (NestJS) participant SA as Supabase Auth participant T as TenantContext (AsyncLocalStorage) participant S as Service de dominio participant P as PrismaService (middleware tx) participant DB as PostgreSQL (RLS) U->>C: Accion (ej. ver agenda del congreso) C->>G: HTTP + Authorization Bearer JWT G->>SA: Verifica firma y expiracion del JWT SA-->>G: JWT valido (claims: user_id, organizacion_id, rol) G->>T: Guarda { organizacion_id, rol } en el contexto de la peticion G->>S: Continua hacia el handler autorizado S->>P: prisma.$transaction(...) para leer/escribir Note over P,DB: El middleware de Prisma abre la transaccion y ejecuta primero: P->>DB: SET LOCAL app.org_id = '<organizacion_id>' P->>DB: SELECT * FROM sesion WHERE congreso_id = $1 Note over DB: La politica RLS anade implicitamente:<br/>USING (organizacion_id = current_setting('app.org_id')::uuid) DB-->>P: Solo filas de la organizacion del tenant P-->>S: Datos ya aislados S-->>C: Respuesta JSON C-->>U: Render de la agenda (solo su organizacion) rect rgb(240, 220, 220) Note over G,DB: Si falta el JWT o el org_id, la variable app.org_id queda vacia<br/>y RLS no devuelve ninguna fila -> denegar por defecto (fail-closed). end
